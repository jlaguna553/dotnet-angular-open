Este capítulo es una **vertical slice**: una pieza pequeña, pero completa, que atraviesa base de datos, servidor y navegador. Al terminar tendrás una aplicación de tareas donde puedes listar, crear, completar y eliminar registros.

La app no intenta esconder la complejidad detrás de una plantilla. Cada decisión está a la vista para que puedas cambiarla después.

## El resultado que vamos a construir

La arquitectura será deliberadamente pequeña:

```text
browser (Angular 17+)
        │ HTTP / JSON
        ▼
ASP.NET Core 8 Minimal API
        │ EF Core
        ▼
SQLite (tasks.db)
```

Cada capa de ese diagrama es una tecnología con un rol concreto. **ASP.NET Core** es el framework de Microsoft para construir servidores web en C# — es lo que recibe la petición HTTP y decide qué código ejecutar. **SQLite** es el motor de base de datos: un programa que guarda tus datos en un archivo y sabe responder consultas sobre ellos.

Entre ambos falta una pieza: tu código C# trabaja con **objetos** (una clase `TaskItem` con propiedades), pero SQLite solo entiende **SQL** (`SELECT * FROM Tasks WHERE ...`). Traducir entre esos dos mundos a mano —escribir el SQL, ejecutarlo, convertir cada fila del resultado de vuelta a un objeto `TaskItem`— es exactamente el trabajo repetitivo que quieres evitar. Ahí entra **EF Core** (*Entity Framework Core*, así, con esas iniciales): un **ORM** (*Object-Relational Mapper*, "mapeador objeto-relacional") de Microsoft que hace esa traducción por ti. Le describes tus datos como clases de C# normales, y EF Core se encarga de generar el SQL, ejecutarlo contra SQLite (o Postgres, o SQL Server — con solo cambiar el "proveedor", como verás en el paso 1), y devolverte objetos ya listos para usar. En el paso 3 vas a escribir tu primer `DbContext`, que es la pieza concreta de EF Core con la que vas a interactuar.

El recurso principal es `TaskItem`:

| Método | Ruta | Acción |
| --- | --- | --- |
| `GET` | `/api/tasks` | Devuelve tareas ordenadas por fecha |
| `POST` | `/api/tasks` | Crea una tarea |
| `PATCH` | `/api/tasks/{id}` | Cambia el estado completado |
| `DELETE` | `/api/tasks/{id}` | Elimina una tarea |

## 1. Crea la solución

Separa backend y frontend desde el primer día. Esto hace visibles los límites y permite desplegarlos de forma independiente — el mismo principio de "cliente-servidor" de la parte 0. Vas a crear tres cosas distintas, cada una con un propósito concreto: una *solución* de .NET (el archivo que agrupa proyectos backend), el proyecto de la API en sí, y el proyecto de Angular como carpeta hermana, no anidada dentro de la API.

Primero, la carpeta raíz y la solución:

<CodeBlock lang="bash" title="Terminal">
```bash
mkdir taskboard && cd taskboard
dotnet new sln -n Taskboard
```
</CodeBlock>

`dotnet new sln` crea `Taskboard.sln`, un archivo vacío que **agrupa proyectos** de .NET para poder compilarlos, testearlos o abrirlos juntos en el editor — todavía no contiene ningún código. Hoy vas a añadirle un solo proyecto, pero en la parte 10 esta misma solución va a crecer a cuatro (`Domain`, `Application`, `Infrastructure`, `Api`); tenerla desde ahora evita reestructurar más adelante.

Ahora el proyecto de la API:

<CodeBlock lang="bash" title="Terminal">
```bash
dotnet new web -n Taskboard.Api
dotnet sln add Taskboard.Api/Taskboard.Api.csproj
```
</CodeBlock>

- `dotnet new web -n Taskboard.Api` genera el proyecto ASP.NET Core más pequeño que existe: solo un `Program.cs` y un `.csproj`, sin controladores ni carpetas de MVC — la plantilla `web` es, precisamente, la que usan las Minimal API que vas a construir en este capítulo. `-n` nombra tanto el proyecto como la carpeta que crea.
- `dotnet sln add ...` **no ocurre automáticamente**: crear un proyecto y registrarlo en la solución son dos pasos separados. Sin este comando, `Taskboard.Api` existiría en el disco pero `dotnet build` a nivel de solución lo ignoraría.

Así se ve `Taskboard.Api.csproj` justo después de crearlo — este es el archivo XML que describe el proyecto, y todavía no tiene ningún paquete instalado:

<CodeBlock lang="xml" title="Taskboard.Api/Taskboard.Api.csproj (recién creado)">
```xml
<Project Sdk="Microsoft.NET.Sdk.Web">

  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>

</Project>
```
</CodeBlock>

Y el proyecto de Angular, como carpeta hermana de `Taskboard.Api` (no dentro de ella):

<CodeBlock lang="bash" title="Terminal">
```bash
ng new taskboard-web --standalone --routing --style=scss --skip-git
```
</CodeBlock>

Cada flag es una decisión explícita, no un valor arbitrario:

| Flag | Qué hace | Por qué lo usamos aquí |
| --- | --- | --- |
| `--standalone` | Genera componentes sin `NgModule` | Es el enfoque que vas a usar en toda la guía, a partir de la parte 1 |
| `--routing` | Crea `app.routes.ts` con el Router configurado | Este quickstart no navega entre páginas todavía, pero lo necesitarás desde la parte 5 (pantalla de login) |
| `--style=scss` | Usa Sass en vez de CSS plano para las hojas de estilo | Sass te da variables y anidamiento sin coste — puedes escribir CSS normal dentro de un archivo `.scss` si no lo necesitas aún |
| `--skip-git` | No inicializa un repositorio git dentro de `taskboard-web/` | `ng new` crea su propio repo por defecto; lo evitamos porque `taskboard/` en su conjunto será un único repositorio |

Angular CLI te va a preguntar interactivamente sobre Server-Side Rendering (SSR) — responde que no (`N`) por ahora; es el tema que se menciona brevemente en la parte 0 y que queda fuera del alcance de este curso.

### Añade EF Core y las herramientas de migración

Con los dos proyectos creados, instala en `Taskboard.Api` lo necesario para hablar con una base de datos:

<CodeBlock lang="bash" title="Terminal">
```bash
cd Taskboard.Api
dotnet add package Microsoft.EntityFrameworkCore.Sqlite --version 8.*
dotnet add package Microsoft.EntityFrameworkCore.Design --version 8.*
dotnet tool install --global dotnet-ef
cd ..
```
</CodeBlock>

Cada `dotnet add package <nombre>` descarga un **paquete de NuGet** — el registro de librerías de .NET, el equivalente exacto del npm que acabas de usar para instalar Angular CLI — y lo añade como referencia dentro de `Taskboard.Api.csproj` (el archivo XML que lista, entre otras cosas, qué paquetes usa el proyecto).

Son tres piezas distintas, y vale la pena distinguirlas:

- **`Microsoft.EntityFrameworkCore.Sqlite`** es el *proveedor*: la pieza que sabe traducir las operaciones de EF Core al SQL específico de SQLite. Cada motor de base de datos necesita su propio proveedor — en la parte 4 vas a sustituir este paquete por `Npgsql.EntityFrameworkCore.PostgreSQL` sin cambiar ninguna otra línea de código.
- **`Microsoft.EntityFrameworkCore.Design`** trae las herramientas necesarias **solo en tiempo de desarrollo** para generar migraciones (`dotnet ef migrations add`, que verás en el paso 5). No la necesita la aplicación cuando corre en producción, pero sí el propio comando `dotnet ef` para inspeccionar tu proyecto y generar el código de la migración.
- **`dotnet tool install --global dotnet-ef`** es distinto a los dos anteriores: no es un paquete NuGet que se referencia desde el `.csproj`, sino una **herramienta de línea de comandos** que se instala una sola vez en tu máquina (`--global`) y queda disponible como `dotnet ef` en cualquier proyecto, no solo en Taskboard. Por eso, a diferencia de los otros dos comandos, este no deja ningún rastro dentro de `Taskboard.Api.csproj`.

Así se ve el mismo `Taskboard.Api.csproj` después de los dos `dotnet add package` — compáralo con la versión de más arriba:

<CodeBlock lang="xml" title="Taskboard.Api/Taskboard.Api.csproj (después de instalar EF Core)">
```xml
<Project Sdk="Microsoft.NET.Sdk.Web">

  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Microsoft.EntityFrameworkCore.Design" Version="8.0.10" />
    <PackageReference Include="Microsoft.EntityFrameworkCore.Sqlite" Version="8.0.10" />
  </ItemGroup>

</Project>
```
</CodeBlock>

Apareció un `<ItemGroup>` nuevo con una línea `<PackageReference>` por cada paquete — tú no editaste este archivo a mano, `dotnet add package` lo hizo por ti. El número de versión que veas puede no ser exactamente `8.0.10`: NuGet resuelve automáticamente la versión más reciente compatible con el rango `8.*` que pediste, en el momento en que ejecutaste el comando. Para quitar una dependencia más adelante, el comando inverso es `dotnet remove package <nombre>` — borra la línea correspondiente de este mismo archivo.

## 2. Modela el dominio

Crea `Taskboard.Api/Models/TaskItem.cs`. El modelo representa datos persistidos, no el formulario de entrada. `CreatedAt` lo controla el servidor para que el cliente no pueda falsificarlo.

<CodeBlock lang="csharp" title="Models/TaskItem.cs">
```csharp
namespace Taskboard.Api.Models;

public sealed class TaskItem
{
    public int Id { get; set; }
    public required string Title { get; set; }
    public bool IsCompleted { get; set; }
    public DateTime CreatedAt { get; set; }
}
```
</CodeBlock>

Línea por línea:

- **`namespace Taskboard.Api.Models;`** — agrupa este archivo bajo el espacio de nombres `Taskboard.Api.Models`. En C#, el namespace normalmente refleja la carpeta (`Models/`) y es lo que te permite tener dos clases con el mismo nombre en carpetas distintas sin que choquen; también es lo que vas a escribir en un `using` cuando quieras usar esta clase desde otro archivo.
- **`public sealed class TaskItem`** — `public` significa que cualquier otro archivo del proyecto (o de otro proyecto que lo referencie) puede usar esta clase. `sealed` significa que nadie puede crear una clase que herede de `TaskItem` — una decisión deliberada: este modelo no está diseñado para extenderse por herencia, solo para instanciarse directamente.
- **`public int Id { get; set; }`** — una **propiedad automática**: `{ get; set; }` le dice al compilador que genere por ti un método para leer (`get`) y otro para escribir (`set`) el valor, sin que tengas que declarar un campo privado a mano. `int` es un número entero; EF Core, más adelante, va a configurar esta propiedad como clave primaria autoincremental por convención (porque se llama `Id`).
- **`public required string Title { get; set; }`** — `required` (C# 11) obliga a que, en cualquier lugar donde crees un `TaskItem`, tengas que asignarle un `Title` explícitamente — si lo olvidas, el compilador rechaza tu código antes de que llegue a ejecutarse. Es la forma que tiene C# de decir "este dato no es opcional" sin depender de una validación en tiempo de ejecución.
- **`public bool IsCompleted { get; set; }`** — un valor de verdadero/falso. Al no tener `required`, C# le asigna automáticamente su valor por defecto (`false`) si no lo especificas — que es exactamente el comportamiento que quieres: una tarea nueva empieza sin completar.
- **`public DateTime CreatedAt { get; set; }`** — una fecha y hora. Fíjate que **ningún endpoint va a dejar que el cliente escriba este valor** — lo vas a ver en el paso 4, donde el servidor lo asigna con `DateTime.UtcNow` en el momento de crear la tarea, precisamente para que el navegador no pueda falsificarlo.

Para evitar aceptar campos que no deberían llegar desde el navegador, define contratos explícitos en `Contracts/TaskContracts.cs`:

<CodeBlock lang="csharp" title="Contracts/TaskContracts.cs">
```csharp
namespace Taskboard.Api.Contracts;

public sealed record CreateTaskRequest(string Title);
public sealed record UpdateTaskRequest(bool IsCompleted);
public sealed record TaskResponse(
    int Id,
    string Title,
    bool IsCompleted,
    DateTime CreatedAt);
```
</CodeBlock>

`record` es un tipo de C# pensado para datos inmutables: escribir `public sealed record CreateTaskRequest(string Title);` genera automáticamente el constructor, la comparación por valor (dos records son "iguales" si sus datos coinciden, no solo si son el mismo objeto en memoria) y una representación en texto legible — todo lo que tendrías que escribir a mano con una `class` tradicional. Es la elección natural para contratos que solo transportan datos entre capas, sin comportamiento propio. La sintaxis `record NombreDelTipo(Tipo Propiedad, ...)` entre paréntesis es una forma abreviada de escribir el record entero en una sola línea, con una propiedad de solo lectura por cada parámetro.

Fíjate que ningún record repite exactamente los campos de `TaskItem`, y eso es intencional, no un descuido:

- **`CreateTaskRequest(string Title)`** — solo `Title`. Es lo único que el cliente debería poder decidir al crear una tarea; `Id` lo asigna la base de datos, `CreatedAt` lo asigna el servidor, e `IsCompleted` siempre empieza en `false`. Si este record tuviera un campo `Id`, un cliente malicioso podría intentar crear una tarea con un id ya existente.
- **`UpdateTaskRequest(bool IsCompleted)`** — solo el campo que el endpoint de actualización (`PATCH`, en el paso 4) tiene sentido que cambie. No permite modificar el título ni la fecha de creación desde esta operación.
- **`TaskResponse(int Id, string Title, bool IsCompleted, DateTime CreatedAt)`** — el único de los tres que sí expone los cuatro campos, porque es lo que el servidor le **devuelve** al cliente después de leer o crear una tarea; el cliente necesita el `Id` para poder referirse a esa tarea en peticiones futuras (`PATCH /api/tasks/{id}`).

La respuesta pública no tiene por qué coincidir con la entidad de EF Core. Esa pequeña separación evita acoplar tu API a futuras decisiones de persistencia.

## 3. Configura EF Core y SQLite

Crea `Data/TaskDbContext.cs`:

<CodeBlock lang="csharp" title="Data/TaskDbContext.cs">
```csharp
using Microsoft.EntityFrameworkCore;
using Taskboard.Api.Models;

namespace Taskboard.Api.Data;

public sealed class TaskDbContext(DbContextOptions<TaskDbContext> options)
    : DbContext(options)
{
    public DbSet<TaskItem> Tasks => Set<TaskItem>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<TaskItem>(entity =>
        {
            entity.Property(task => task.Title)
                .HasMaxLength(160)
                .IsRequired();

            entity.Property(task => task.CreatedAt)
                .HasDefaultValueSql("CURRENT_TIMESTAMP");
        });
    }
}
```
</CodeBlock>

Línea por línea:

- **`using Microsoft.EntityFrameworkCore;`** y **`using Taskboard.Api.Models;`** — importan, respectivamente, los tipos de EF Core (`DbContext`, `DbSet`, `ModelBuilder`...) y tu propio `TaskItem`. Sin el primero, el compilador no reconocería `DbContext` ni `ModelBuilder`.
- **`public sealed class TaskDbContext(DbContextOptions<TaskDbContext> options) : DbContext(options)`** — usa **constructores primarios** (C# 12): los parámetros entre paréntesis junto al nombre de la clase reemplazan escribir un constructor y un campo privado por separado. `: DbContext(options)` hereda de la clase base de EF Core y le reenvía esas opciones (que incluyen, entre otras cosas, qué base de datos usar — lo verás configurado en el paso 4). Nunca vas a escribir `new TaskDbContext(...)` en ningún lado: quién construye esta clase, y cuándo, es exactamente lo que verás en el siguiente paso (inyección de dependencias).
- **`public DbSet<TaskItem> Tasks => Set<TaskItem>();`** — un `DbSet<TaskItem>` representa, conceptualmente, "la tabla de tareas": es el objeto sobre el que vas a escribir consultas (`database.Tasks.Where(...)`) y cambios (`database.Tasks.Add(...)`). La flecha `=>` es una **propiedad con cuerpo de expresión**: en vez de un `{ get { return ...; } }` completo, es una forma corta de decir "cada vez que alguien lea `Tasks`, devuelve el resultado de `Set<TaskItem>()`" (un método heredado de `DbContext` que localiza o crea ese `DbSet` internamente).
- **`protected override void OnModelCreating(ModelBuilder modelBuilder)`** — un método que **EF Core llama automáticamente**, una sola vez, cuando construye el modelo por primera vez — tú nunca lo invocas directamente. `protected` porque solo la propia clase (y quien herede de ella) necesita implementarlo; `override` porque estás reemplazando la versión vacía que trae `DbContext` por defecto.
- **`modelBuilder.Entity<TaskItem>(entity => { ... })`** — le dice a EF Core "voy a configurar reglas específicas para la tabla que representa a `TaskItem`". Todo lo que va dentro de las llaves usa la variable `entity` para referirse a esa configuración — este estilo, donde encadenas métodos que van devolviendo el mismo objeto para seguir configurando, se llama **fluent API**.
- **`entity.Property(task => task.Title).HasMaxLength(160).IsRequired();`** — `task => task.Title` es una expresión lambda que apunta a la propiedad `Title` (en vez de pasar el nombre como texto plano `"Title"`, lo que te daría un error de compilación si algún día renombras la propiedad, no un fallo silencioso en producción). `.HasMaxLength(160)` limita la columna a 160 caracteres en la base de datos; `.IsRequired()` la marca como `NOT NULL`.
- **`entity.Property(task => task.CreatedAt).HasDefaultValueSql("CURRENT_TIMESTAMP");`** — le dice a SQLite que, si nadie especifica un valor para esta columna al insertar una fila, use la fecha y hora actuales por defecto. Es una capa extra de seguridad además de que el propio C# ya asigna `DateTime.UtcNow` en el paso 4 — si algún día insertas datos directamente en SQL sin pasar por tu API, la columna sigue teniendo un valor razonable.

En `appsettings.json`, configura la conexión con un archivo local. En producción sustituirás esta cadena por una variable de entorno.

<CodeBlock lang="json" title="appsettings.json">
```json
{
  "ConnectionStrings": {
    "Taskboard": "Data Source=taskboard.db"
  },
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  }
}
```
</CodeBlock>

- **`"ConnectionStrings": { "Taskboard": "Data Source=taskboard.db" }`** — una cadena de conexión le dice a EF Core dónde y cómo conectarse a la base de datos; su formato depende del proveedor (para SQLite, `Data Source=<archivo>` basta). `"Taskboard"` es solo el nombre que le diste a esta entrada — es el mismo string que vas a usar para leerla en el paso 4 con `GetConnectionString("Taskboard")`. Al ejecutar la API, SQLite crea el archivo `taskboard.db` en la carpeta desde la que corres `dotnet run`, si todavía no existe.
- **`"Logging": { "LogLevel": { "Default": "Information", "Microsoft.AspNetCore": "Warning" } }`** — controla qué tan detallados son los mensajes que la aplicación escribe en la consola. `"Default": "Information"` es el nivel general (verás mensajes informativos de tu propio código); `"Microsoft.AspNetCore": "Warning"` sube el umbral solo para los mensajes que genera el propio framework, para no inundar la consola con detalles internos de ASP.NET Core que rara vez necesitas mientras desarrollas.

## 4. Construye la API Minimal

Reemplaza el contenido de `Program.cs`. La aplicación registra CORS para el servidor de desarrollo de Angular, crea la base de datos al arrancar y expone cuatro operaciones HTTP.

<CodeBlock lang="csharp" title="Program.cs">
```csharp
using Microsoft.EntityFrameworkCore;
using Taskboard.Api.Contracts;
using Taskboard.Api.Data;
using Taskboard.Api.Models;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<TaskDbContext>(options =>
    options.UseSqlite(builder.Configuration.GetConnectionString("Taskboard")));

builder.Services.AddCors(options =>
{
    options.AddPolicy("AngularDev", policy => policy
        .WithOrigins("http://localhost:4200")
        .AllowAnyHeader()
        .AllowAnyMethod());
});

var app = builder.Build();

app.UseCors("AngularDev");

using (var scope = app.Services.CreateScope())
{
    var database = scope.ServiceProvider.GetRequiredService<TaskDbContext>();
    await database.Database.MigrateAsync();
}

app.MapGet("/api/tasks", async (TaskDbContext database, CancellationToken cancellationToken) =>
{
    var tasks = await database.Tasks
        .AsNoTracking()
        .OrderByDescending(task => task.CreatedAt)
        .Select(task => new TaskResponse(
            task.Id,
            task.Title,
            task.IsCompleted,
            task.CreatedAt))
        .ToListAsync(cancellationToken);

    return Results.Ok(tasks);
});

app.MapPost("/api/tasks", async (
    CreateTaskRequest request,
    TaskDbContext database,
    CancellationToken cancellationToken) =>
{
    var title = request.Title.Trim();
    if (title.Length is < 1 or > 160)
    {
        return Results.ValidationProblem(new Dictionary<string, string[]>
        {
            [nameof(request.Title)] = ["Escribe entre 1 y 160 caracteres."]
        });
    }

    var task = new TaskItem
    {
        Title = title,
        CreatedAt = DateTime.UtcNow
    };

    database.Tasks.Add(task);
    await database.SaveChangesAsync(cancellationToken);

    return Results.Created($"/api/tasks/{task.Id}", new TaskResponse(
        task.Id, task.Title, task.IsCompleted, task.CreatedAt));
});

app.MapPatch("/api/tasks/{id:int}", async (
    int id,
    UpdateTaskRequest request,
    TaskDbContext database,
    CancellationToken cancellationToken) =>
{
    var task = await database.Tasks.FindAsync([id], cancellationToken);
    if (task is null)
    {
        return Results.NotFound();
    }

    task.IsCompleted = request.IsCompleted;
    await database.SaveChangesAsync(cancellationToken);
    return Results.NoContent();
});

app.MapDelete("/api/tasks/{id:int}", async (
    int id,
    TaskDbContext database,
    CancellationToken cancellationToken) =>
{
    var deleted = await database.Tasks
        .Where(task => task.Id == id)
        .ExecuteDeleteAsync(cancellationToken);

    return deleted == 0 ? Results.NotFound() : Results.NoContent();
});

app.Run();

public partial class Program { }
```
</CodeBlock>

### La configuración inicial, línea por línea

- **`var builder = WebApplication.CreateBuilder(args);`** — el punto de partida de cualquier app ASP.NET Core moderna: crea un "constructor" que sabe leer `appsettings.json`, las variables de entorno y los argumentos de línea de comandos (`args`), y que vas a usar para registrar servicios antes de arrancar la aplicación de verdad.
- **`builder.Services.AddDbContext<TaskDbContext>(options => options.UseSqlite(builder.Configuration.GetConnectionString("Taskboard")));`** — `builder.Services` es el contenedor de inyección de dependencias del que ya hablamos en el paso 3: aquí le estás enseñando **cómo** construir un `TaskDbContext` cuando algún endpoint lo pida. `options => options.UseSqlite(...)` es una función que configura ese `TaskDbContext` para usar el proveedor de SQLite (el paquete que instalaste en el paso 1), leyendo la cadena de conexión `"Taskboard"` que definiste en `appsettings.json` un momento atrás.
- **`builder.Services.AddCors(options => { options.AddPolicy("AngularDev", policy => policy.WithOrigins("http://localhost:4200").AllowAnyHeader().AllowAnyMethod()); });`** — registra una **política de CORS** (*Cross-Origin Resource Sharing*) llamada `"AngularDev"`. Por defecto, los navegadores bloquean que una página servida desde un origen (`http://localhost:4200`, donde corre Angular) haga peticiones a otro origen distinto (`http://localhost:5000`, donde corre la API) — CORS es el mecanismo por el cual el servidor le dice explícitamente al navegador "confío en peticiones que vienen de este origen". `.WithOrigins(...)` especifica cuál; `.AllowAnyHeader()` y `.AllowAnyMethod()` permiten cualquier encabezado y cualquier verbo HTTP (`GET`, `POST`, etc.) desde ese origen.
- **`var app = builder.Build();`** — a partir de aquí, ya no puedes registrar más servicios (`builder.Services...`) — `Build()` "sella" la configuración y te da la aplicación ya construida, sobre la que vas a definir el pipeline de middleware y los endpoints.
- **`app.UseCors("AngularDev");`** — activa, dentro del pipeline de la aplicación, la política de CORS que registraste arriba. Sin esta línea, `AddCors` habría quedado configurado pero nunca aplicado a ninguna petición real.
- **El bloque `using (var scope = app.Services.CreateScope()) { ... }`** — ejecuta la migración de la base de datos (`await database.Database.MigrateAsync();`) una sola vez, al arrancar la aplicación, aplicando cualquier migración pendiente (la que vas a crear en el paso 5) sin que tengas que correr `dotnet ef database update` manualmente cada vez que despliegues. Necesita un `scope` explícito (en vez de pedir el `TaskDbContext` directamente) porque, a diferencia de dentro de un endpoint, aquí todavía no hay una petición HTTP en curso que le proporcione uno automáticamente — `CreateScope()` crea uno "de mentira", solo para este arranque, y `GetRequiredService<TaskDbContext>()` es cómo le pides al contenedor de DI que te entregue una instancia dentro de ese scope.

### Los cuatro endpoints

Antes de los detalles puntuales, dos conceptos que se repiten en **cada** uno y que vale la pena nombrar:

- **Inyección de dependencias (DI).** Fíjate que en `(TaskDbContext database, CancellationToken cancellationToken) => { ... }` nunca escribes `new TaskDbContext(...)` — `database` simplemente aparece como parámetro, ya listo para usar. Esto es DI: le dijiste al framework, con `AddDbContext<TaskDbContext>(...)` arriba, *cómo* construir un `TaskDbContext` cuando alguien lo necesite. ASP.NET Core inspecciona los parámetros de cada handler, reconoce que pide un `TaskDbContext`, y te entrega una instancia ya configurada — una nueva por cada petición HTTP. Vas a ver la misma idea, con otro nombre (`inject()`), del lado de Angular en el paso 7.
- **`async`/`await` y `CancellationToken`.** Marcar un método como `async` y usar `await` dentro le permite al servidor seguir atendiendo otras peticiones mientras espera algo lento —aquí, una consulta a la base de datos— en lugar de bloquear un hilo sin hacer nada mientras tanto. `CancellationToken` es una señal que ASP.NET Core te pasa automáticamente y que se activa si el cliente cierra la conexión antes de que termines de responder, para que puedas abandonar el trabajo a medio hacer en vez de completarlo igual sin que nadie vaya a leer el resultado.

**`app.MapGet("/api/tasks", async (TaskDbContext database, CancellationToken cancellationToken) => { ... });`** — `"/api/tasks"` es la ruta; todo lo que sigue es el *handler*, la función que se ejecuta cuando llega esa petición.

- `database.Tasks` — el `DbSet<TaskItem>` del paso 3: el punto de partida de la consulta.
- `.AsNoTracking()` — le dice a EF Core que no necesita llevar un registro interno de estos objetos para detectar cambios más adelante — algo que EF Core hace por defecto pensando en que quizás quieras modificarlos y guardarlos después. Como este endpoint solo lee datos para mostrarlos, desactivarlo hace la consulta más liviana.
- `.OrderByDescending(task => task.CreatedAt)` — ordena el resultado de más reciente a más antiguo, usando la misma sintaxis de lambda que ya viste en `OnModelCreating`.
- `.Select(task => new TaskResponse(task.Id, task.Title, task.IsCompleted, task.CreatedAt))` — transforma cada `TaskItem` (la entidad de EF Core) en un `TaskResponse` (el contrato del paso 2) — este es, en código, el momento exacto donde ocurre la separación entre "lo que guardas" y "lo que expones" de la que hablamos en el paso 2.
- `.ToListAsync(cancellationToken)` — ejecuta la consulta contra la base de datos y espera el resultado como una lista; es aquí, no antes, donde realmente se dispara el SQL (todo lo anterior solo iba construyendo la consulta).
- `Results.Ok(tasks)` — construye una respuesta HTTP `200 OK` con `tasks` serializado como JSON en el cuerpo.

**`app.MapPost("/api/tasks", async (CreateTaskRequest request, TaskDbContext database, CancellationToken cancellationToken) => { ... });`** — ASP.NET Core reconoce que `CreateTaskRequest` no es un tipo conocido del framework (como `TaskDbContext` o `CancellationToken`) y, por convención, asume que debe **deserializarlo del cuerpo JSON de la petición**.

- `request.Title.Trim()` — quita espacios en blanco al principio y al final antes de validar o guardar; así `"  Comprar leche  "` y `"Comprar leche"` se tratan como el mismo título.
- `if (title.Length is < 1 or > 160)` — el patrón `is < 1 or > 160` (C# 9) es una forma compacta de escribir `title.Length < 1 || title.Length > 160`. Si el título queda vacío después del `Trim()`, o supera el límite que configuraste en `HasMaxLength(160)`, se rechaza.
- `Results.ValidationProblem(new Dictionary<string, string[]> { [nameof(request.Title)] = ["Escribe entre 1 y 160 caracteres."] })` — construye una respuesta `400 Bad Request` con el formato estándar de errores de validación de ASP.NET Core. `nameof(request.Title)` produce el texto `"Title"` sin escribirlo a mano — si algún día renombras la propiedad, este texto se actualiza solo. El valor es un arreglo de strings porque un mismo campo podría tener varios mensajes de error a la vez.
- `var task = new TaskItem { Title = title, CreatedAt = DateTime.UtcNow };` — aquí es donde el servidor, y no el cliente, decide el valor de `CreatedAt` — la razón por la que `CreateTaskRequest` nunca incluyó ese campo.
- `database.Tasks.Add(task);` seguido de `await database.SaveChangesAsync(cancellationToken);` — son dos pasos separados a propósito: `Add` solo marca el objeto como "pendiente de insertar" en memoria; `SaveChangesAsync` es el que realmente ejecuta el `INSERT` contra SQLite. Entre ambas líneas podrías, en teoría, añadir más cambios (otra tarea, una actualización) y se guardarían todos juntos en una sola operación.
- `Results.Created($"/api/tasks/{task.Id}", new TaskResponse(...))` — construye un `201 Created`. El primer argumento es la URL del recurso recién creado (va en el encabezado HTTP `Location`); fíjate que `task.Id` ya tiene un valor aquí, aunque tú nunca lo asignaste — SQLite se lo asignó automáticamente al ejecutar el `INSERT`, y EF Core actualizó el objeto `task` en memoria con ese valor.

**`app.MapPatch("/api/tasks/{id:int}", async (int id, UpdateTaskRequest request, TaskDbContext database, CancellationToken cancellationToken) => { ... });`** — `{id:int}` es un **parámetro de ruta con restricción de tipo**: captura el segmento de la URL que ocupa `{id}` (por ejemplo, el `7` en `/api/tasks/7`) y le exige a ASP.NET Core que sea un número entero — si alguien pide `/api/tasks/abc`, la ruta ni siquiera coincide, y responde `404` antes de que tu código se ejecute.

- `await database.Tasks.FindAsync([id], cancellationToken);` — busca una fila por su clave primaria. `FindAsync` recibe un arreglo (`[id]`) porque, en general, una clave primaria puede estar compuesta de varias columnas; aquí solo tiene una.
- `if (task is null) return Results.NotFound();` — si no existe ninguna tarea con ese id, corta la ejecución con un `404`, en vez de seguir adelante con un objeto que no existe.
- `task.IsCompleted = request.IsCompleted;` — a diferencia de `Create`, aquí sí modificas directamente el objeto que EF Core te devolvió (porque este `FindAsync`, a diferencia del `AsNoTracking()` de `GetAll`, sí lo está rastreando) — es lo que le permite a `SaveChangesAsync` detectar qué cambió y generar el `UPDATE` correspondiente.
- `Results.NoContent()` — un `204`: la operación tuvo éxito, pero no hay nada que devolver en el cuerpo (el cliente ya sabe qué cambió, porque fue quien lo pidió).

**`app.MapDelete("/api/tasks/{id:int}", async (int id, TaskDbContext database, CancellationToken cancellationToken) => { ... });`**

- `database.Tasks.Where(task => task.Id == id).ExecuteDeleteAsync(cancellationToken)` — a diferencia de `UpdateStatus`, este endpoint no busca primero el objeto y luego lo borra: `ExecuteDeleteAsync` traduce la condición del `Where` directamente a un `DELETE ... WHERE Id = @id` en SQL, sin traer la fila a memoria primero — más eficiente cuando no necesitas el objeto para nada más que borrarlo. Devuelve cuántas filas se borraron.
- `return deleted == 0 ? Results.NotFound() : Results.NoContent();` — un operador ternario: si no se borró ninguna fila (el id no existía), `404`; si se borró una, `204`.

Y tres detalles más, sobre el archivo en su conjunto:

1. `Results.Created` devuelve el recurso creado y su URL en el encabezado `Location`, como ya viste en `MapPost`.
2. Cada handler recibe exactamente los parámetros que necesita (`TaskDbContext`, `CancellationToken`, el `id` de ruta, el cuerpo deserializado) — ASP.NET Core los resuelve a todos de la misma forma, combinando DI con los datos de la petición HTTP.
3. `public partial class Program { }`, al final del archivo, permite que los tests de integración (parte 11) encuentren el *entry point* de tu aplicación para levantarla en memoria durante un test — sin esta línea, la clase `Program` que genera `dotnet new web` internamente no sería accesible desde fuera del proyecto.

## 5. Crea la migración

El modelo de C# todavía no es una tabla. Una migración convierte ese cambio en instrucciones reproducibles:

<CodeBlock lang="bash" title="Taskboard.Api/">
```bash
dotnet ef migrations add InitialCreate
dotnet ef database update
dotnet run
```
</CodeBlock>

`dotnet ef migrations add InitialCreate` todavía no toca ninguna base de datos — genera código C# que **describe** el cambio. Después de ejecutarlo, aparece una carpeta nueva que tú no escribiste a mano:

<CodeBlock lang="text" title="Taskboard.Api/">
```text
Taskboard.Api/
└── Migrations/
    ├── 20260907120000_InitialCreate.cs           — instrucciones Up()/Down() de este cambio
    ├── 20260907120000_InitialCreate.Designer.cs  — metadatos que usa el propio EF Core
    └── TaskDbContextModelSnapshot.cs             — una "foto" completa del modelo actual
```
</CodeBlock>

Y dentro de `InitialCreate.cs`, el método `Up()` —el que se ejecuta al aplicar la migración— contiene, generado automáticamente a partir de tu clase `TaskItem`, algo equivalente a esto:

<CodeBlock lang="csharp" title="Migrations/..._InitialCreate.cs (generado, no lo escribes tú)">
```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.CreateTable(
        name: "Tasks",
        columns: table => new
        {
            Id = table.Column<int>(type: "INTEGER", nullable: false)
                .Annotation("Sqlite:Autoincrement", true),
            Title = table.Column<string>(type: "TEXT", maxLength: 160, nullable: false),
            IsCompleted = table.Column<bool>(type: "INTEGER", nullable: false),
            CreatedAt = table.Column<DateTime>(type: "TEXT", nullable: false, defaultValueSql: "CURRENT_TIMESTAMP")
        },
        constraints: table =>
        {
            table.PrimaryKey("PK_Tasks", x => x.Id);
        });
}
```
</CodeBlock>

Cada propiedad de `TaskItem` se convirtió en una columna, y las reglas que declaraste en `OnModelCreating` (`HasMaxLength(160)`, `HasDefaultValueSql(...)`) aparecen tal cual en las columnas correspondientes. `dotnet ef database update` es el paso que **ejecuta** ese `Up()` de verdad — es en ese momento, no antes, cuando el archivo `taskboard.db` aparece en disco con la tabla `Tasks` ya creada.

Visita `http://localhost:5000/api/tasks`. La respuesta inicial será `[]`. Puedes probar una creación con curl:

<CodeBlock lang="bash" title="Otra terminal">
```bash

  -H "Content-Type: application/json" \

```
</CodeBlock>

## 6. Configura Angular Standalone

En `taskboard-web/src/app/models/task.ts`, declara el contrato que consume la UI:

<CodeBlock lang="typescript" title="src/app/models/task.ts">
```typescript
export interface Task {
  id: number;
  title: string;
  isCompleted: boolean;
  createdAt: string;
}

export interface CreateTaskRequest {
  title: string;
}
```
</CodeBlock>

Una `interface` de TypeScript no genera ningún código — desaparece por completo al compilar a JavaScript. Solo le describe a tu editor y al compilador qué forma debe tener un objeto, para que te avisen antes de ejecutar nada si accedes a una propiedad que no existe o le pasas un tipo equivocado a una función.

Fíjate que `Task` y `CreateTaskRequest` reflejan, del lado de Angular, la misma separación que ya viste en `TaskResponse` y `CreateTaskRequest` de C# en el paso 2: `Task` tiene los cuatro campos porque así es como la API te devuelve una tarea, mientras que `CreateTaskRequest` solo tiene `title` porque es lo único que el formulario necesita enviar — `id`, `isCompleted` y `createdAt` los decide el servidor, no el cliente.

Crea un proxy para que el navegador llame a `/api` sin problemas de CORS durante el desarrollo:

<CodeBlock lang="json" title="proxy.conf.json">
```json
{
  "/api": {
    "target": "https://localhost:7123",
    "secure": false,
    "changeOrigin": true
  }
}
```
</CodeBlock>

- **La clave `"/api"`** — cualquier petición que Angular haga a una URL que empiece con `/api` (por ejemplo, `/api/tasks`, tal como lo escribiste en `TaskApiService` un momento más abajo) activa esta regla del proxy.
- **`"target": "https://localhost:7123"`** — a dónde reenviar esa petición de verdad: el puerto real donde corre tu API .NET (el que anotaste al final del paso 5).
- **`"secure": false`** — le dice al proxy que no valide el certificado HTTPS del target. El certificado que usa `dotnet run` en desarrollo es autofirmado (no está avalado por una autoridad reconocida), así que sin esta opción el proxy rechazaría la conexión.
- **`"changeOrigin": true`** — reescribe el encabezado `Host` de la petición para que coincida con el `target`, en vez de conservar `localhost:4200`. Algunos servidores (no es el caso de Kestrel por defecto, pero es una buena práctica general) rechazan peticiones cuyo `Host` no coincide con el dominio al que realmente están escuchando.

Actualiza el script `start` en `package.json` de Angular:

<CodeBlock lang="json" title="taskboard-web/package.json">
```json
{
  "scripts": {
    "start": "ng serve --proxy-config proxy.conf.json"
  }
}
```
</CodeBlock>

`ng serve` por sí solo no sabe nada de tu API — es `--proxy-config proxy.conf.json` lo que le indica que use el archivo que acabas de crear. Este script es lo que se ejecuta cuando escribes `npm start` (lo verás en el paso 9): npm simplemente busca la clave `"start"` dentro de `"scripts"` y corre el comando asociado.

## 7. Encapsula el acceso HTTP

El servicio es la única pieza que conoce las rutas de la API. Esa frontera hace que el componente pueda concentrarse en interacción y estado.

<CodeBlock lang="typescript" title="src/app/services/task-api.service.ts">
```typescript
import { Injectable, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { CreateTaskRequest, Task } from '../models/task';

@Injectable({ providedIn: 'root' })
export class TaskApiService {
  private readonly http = inject(HttpClient);
  private readonly resourceUrl = '/api/tasks';

  getAll(): Observable<Task[]> {
    return this.http.get<Task[]>(this.resourceUrl);
  }

  create(request: CreateTaskRequest): Observable<Task> {
    return this.http.post<Task>(this.resourceUrl, request);
  }

  updateStatus(id: number, isCompleted: boolean): Observable<void> {
    return this.http.patch<void>(`${this.resourceUrl}/${id}`, { isCompleted });
  }

  remove(id: number): Observable<void> {
    return this.http.delete<void>(`${this.resourceUrl}/${id}`);
  }
}
```
</CodeBlock>

Tres piezas nuevas en este servicio, y las tres relacionadas entre sí:

- **`@Injectable({ providedIn: 'root' })`** marca la clase como disponible para el sistema de inyección de dependencias de Angular — la misma idea de DI que viste en el backend en el paso 4, ahora del lado del cliente. `providedIn: 'root'` significa que existe una única instancia compartida por toda la aplicación (un *singleton*), no una nueva cada vez que algo la pide.
- **`inject(HttpClient)`** es cómo `TaskApiService` obtiene esa dependencia: en vez de crear su propio cliente HTTP con `new`, le pide a Angular que le entregue la instancia ya configurada — la que vas a registrar con `provideHttpClient()` a continuación.
- **`Observable<Task[]>`** es el tipo que devuelve cada método de `HttpClient`. Se parece a una `Promise` de JavaScript (representa un valor que llegará más adelante), pero con una diferencia clave: **no hace nada hasta que alguien se suscribe** con `.subscribe(...)`, algo que verás en el paso 8. Puede además emitir varios valores a lo largo del tiempo, en vez de uno solo. Profundizamos en RxJS —la librería detrás de `Observable`— en la parte 2.

Y los cuatro métodos, uno por operación:

- **`getAll()`** — `this.http.get<Task[]>(this.resourceUrl)` hace una petición `GET` a `/api/tasks` y le dice a TypeScript, con `<Task[]>`, qué forma esperar en la respuesta — no es una conversión real (TypeScript no valida en tiempo de ejecución que el JSON tenga esa forma), es una promesa que le haces al compilador para que te avise si usas el resultado incorrectamente.
- **`create(request)`** — `this.http.post<Task>(this.resourceUrl, request)`: el segundo argumento de `post` es el cuerpo de la petición — Angular lo serializa a JSON automáticamente. Coincide exactamente con el `CreateTaskRequest` que espera `MapPost` del lado de .NET.
- **`updateStatus(id, isCompleted)`** — ``this.http.patch<void>(`${this.resourceUrl}/${id}`, { isCompleted })`` arma la URL con un *template literal* (el texto entre backticks con `${...}` dentro, que interpola una expresión) en vez de concatenar strings con `+`. `<void>` porque el `MapPatch` del backend responde `204 No Content` — no hay ningún cuerpo que esperar de vuelta. `{ isCompleted }` es la forma corta de escribir `{ isCompleted: isCompleted }` cuando el nombre de la propiedad coincide con el de la variable.
- **`remove(id)`** — `this.http.delete<void>(...)`, mismo patrón que `updateStatus` pero sin cuerpo, porque `MapDelete` no necesita ningún dato adicional aparte del `id` que ya va en la URL.

Registra `HttpClient` en `src/app/app.config.ts`:

<CodeBlock lang="typescript" title="src/app/app.config.ts">
```typescript
import { ApplicationConfig } from '@angular/core';
import { provideHttpClient } from '@angular/common/http';
import { provideRouter } from '@angular/router';
import { routes } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideHttpClient(),
  ],
};
```
</CodeBlock>

- **`ApplicationConfig`** — el tipo de un objeto de configuración a nivel de toda la aplicación (a diferencia de `NgModule`, que ya no usas en un proyecto standalone). `ng new --standalone` ya generó este archivo con `provideRouter(routes)` dentro; `provideHttpClient()` es lo único que añades tú.
- **`providers: [...]`** — un arreglo de "proveedores": cada `provide*()` registra algo en el sistema de inyección de dependencias de Angular, disponible para toda la aplicación. `provideRouter(routes)` habilita el enrutador con las rutas de `app.routes.ts` (que `--routing` generó vacías); `provideHttpClient()` es lo que hace posible que `inject(HttpClient)`, dentro de `TaskApiService`, encuentre una instancia real en lugar de fallar.

## 8. Construye el componente

Este componente usa APIs standalone y `@if`/`@for`, el control flow moderno de Angular. El formulario es nativo en este quickstart para mantener el foco en el flujo HTTP; en la parte 2 lo sustituiremos por Reactive Forms.

<CodeBlock lang="typescript" title="src/app/app.component.ts">
```typescript
import { Component, OnInit, inject, signal } from '@angular/core';
import { FormsModule } from '@angular/forms';
import { Task } from './models/task';
import { TaskApiService } from './services/task-api.service';

@Component({
  selector: 'app-root',
  standalone: true,
  imports: [FormsModule],
  templateUrl: './app.component.html',
  styleUrl: './app.component.scss',
})
export class AppComponent implements OnInit {
  private readonly taskApi = inject(TaskApiService);

  readonly tasks = signal<Task[]>([]);
  readonly isLoading = signal(true);
  readonly errorMessage = signal('');
  newTitle = '';

  ngOnInit(): void {
    this.loadTasks();
  }

  loadTasks(): void {
    this.isLoading.set(true);
    this.taskApi.getAll().subscribe({
      next: (tasks) => {
        this.tasks.set(tasks);
        this.isLoading.set(false);
      },
      error: () => {
        this.errorMessage.set('No pudimos cargar las tareas. ¿Está encendida la API?');
        this.isLoading.set(false);
      },
    });
  }

  addTask(): void {
    const title = this.newTitle.trim();
    if (!title) return;

    this.taskApi.create({ title }).subscribe({
      next: (task) => {
        this.tasks.update((tasks) => [task, ...tasks]);
        this.newTitle = '';
      },
      error: () => this.errorMessage.set('La tarea no pudo guardarse.'),
    });
  }

  toggleTask(task: Task): void {
    this.taskApi.updateStatus(task.id, !task.isCompleted).subscribe({
      next: () => this.tasks.update((tasks) => tasks.map((item) =>
        item.id === task.id ? { ...item, isCompleted: !item.isCompleted } : item)),
      error: () => this.errorMessage.set('No pudimos actualizar la tarea.'),
    });
  }

  removeTask(task: Task): void {
    this.taskApi.remove(task.id).subscribe({
      next: () => this.tasks.update((tasks) => tasks.filter((item) => item.id !== task.id)),
      error: () => this.errorMessage.set('No pudimos eliminar la tarea.'),
    });
  }
}
```
</CodeBlock>

Una pieza más que aparece por primera vez: `signal<Task[]>([])` crea un **signal**, un contenedor de estado que Angular sabe leer y "escuchar". Cuando lo actualizas con `.set(...)` o `.update(...)`, Angular sabe exactamente qué parte de la plantilla depende de ese valor y solo repinta eso, sin que tengas que decírselo tú. Por ahora, quédate con dos reglas prácticas: para leer su valor lo **llamas como función** (`tasks()`, nunca `tasks`), y nunca lo mutas directamente (nada de `tasks().push(...)`). Vas a profundizar en signals, junto con `computed` y `effect`, en la parte 1.

Repasemos el resto del archivo, de arriba a abajo:

- **El decorador `@Component({...})`** — le da a Angular los metadatos que necesita para tratar esta clase como un componente: `selector: 'app-root'` es el nombre de etiqueta HTML que representa a este componente (`<app-root>`, la que usa `index.html` para arrancar la aplicación); `standalone: true` es explícito aunque ya sea el valor por defecto; `imports: [FormsModule]` trae `[(ngModel)]`, que vas a usar en la plantilla; `templateUrl` y `styleUrl` apuntan a los archivos HTML y SCSS asociados, en vez de escribir el template inline.
- **`export class AppComponent implements OnInit`** — `implements OnInit` es un compromiso con el compilador: "esta clase va a tener un método `ngOnInit()`". Angular llama a `ngOnInit()` automáticamente una sola vez, justo después de crear el componente — es el lugar convencional para disparar la carga inicial de datos, en vez de hacerlo en el constructor.
- **`private readonly taskApi = inject(TaskApiService);`** — mismo patrón de inyección de dependencias que ya viste dentro de `TaskApiService` en el paso 7, ahora consumiendo ese propio servicio. `private` porque solo esta clase lo necesita; `readonly` porque, una vez asignado, nunca se reemplaza por otra instancia.
- **`newTitle = '';`** — una propiedad de clase normal, no un signal. Es una elección deliberada: este valor solo lo necesita el `[(ngModel)]` del formulario (paso siguiente) para funcionar, y Angular ya sabe re-renderizar el `<input>` que lo usa sin necesitar la maquinaria de un signal — no todo el estado de un componente necesita ser un signal.
- **`ngOnInit(): void { this.loadTasks(); }`** — delega en un método aparte en vez de poner la lógica directamente aquí, para que `loadTasks()` también se pueda llamar de nuevo más adelante (por ejemplo, desde un futuro botón "recargar") sin duplicar código.
- **`loadTasks()`** — `this.isLoading.set(true)` antes de pedir los datos, y `.set(false)` tanto si la petición tiene éxito como si falla (dentro de `next` y de `error` respectivamente) — así la UI siempre sale del estado "cargando", nunca se queda pegada en él. `.subscribe({ next: ..., error: ... })` es cómo consumes un `Observable`: `next` se ejecuta con el valor emitido si todo sale bien, `error` si la petición falla (por ejemplo, si la API no está corriendo).
- **`addTask()`** — valida en el cliente (`if (!title) return;`) antes de siquiera intentar la petición, para no gastar una llamada HTTP en un título vacío — aunque la API también valide del lado del servidor (paso 4), esa doble validación no es redundante: una existe para dar feedback inmediato al usuario, la otra para no confiar nunca en lo que envía el cliente.
- **`this.tasks.update((tasks) => [task, ...tasks])`** — `.update()` recibe el valor actual del signal y devuelve el nuevo; `[task, ...tasks]` crea un **arreglo nuevo** con `task` al principio seguido de todos los elementos anteriores (el operador `...` "esparce" los elementos de `tasks` dentro del arreglo nuevo). Nunca modificas el arreglo original con algo como `.push()` — los signals de Angular detectan cambios comparando referencias, así que necesitas un objeto nuevo, no el mismo mutado.
- **`toggleTask()`** — el mismo patrón de "no mutar", ahora con `.map()`: recorre todas las tareas y devuelve un arreglo nuevo donde, si el `id` coincide, reemplaza esa tarea por una copia (`{ ...item, isCompleted: !item.isCompleted }`) con el campo cambiado; el resto de tareas se devuelven tal cual.
- **`removeTask()`** — `.filter((item) => item.id !== task.id)` devuelve un arreglo nuevo con todas las tareas **excepto** la que coincide — la forma idiomática de "eliminar un elemento" sin mutar el arreglo original.

En los tres métodos de escritura, fíjate en el orden: primero llamas al servicio HTTP, y **solo si tiene éxito** (dentro de `next`) actualizas el signal local — nunca actualizas la UI de forma optimista antes de confirmar que el servidor aceptó el cambio.

La plantilla queda pequeña porque el componente mantiene la lógica en métodos con nombres claros:

```html
<main class="shell">
  <header class="hero">
    <p class="eyebrow">TASKBOARD / QUICKSTART</p>
    <h1>Menos pendientes.<br /><em>Más entregas.</em></h1>
    <p>Una lista mínima para practicar el viaje completo de un dato.</p>
  </header>

  <form class="composer" (ngSubmit)="addTask()">
    <label for="new-task">Nueva tarea</label>
    <div class="composer-row">
      <input id="new-task" name="title" [(ngModel)]="newTitle"
        placeholder="Ej. Publicar la API" maxlength="160" />
      <button type="submit">Añadir</button>
    </div>
  </form>

  @if (errorMessage()) {
    <p class="error" role="alert">{{ errorMessage() }}</p>
  }

  @if (isLoading()) {
    <p class="status">Cargando tareas...</p>
  } @else {
    <ul class="task-list">
      @for (task of tasks(); track task.id) {
        <li [class.completed]="task.isCompleted">
          <button type="button" class="task-title" (click)="toggleTask(task)">
            <span class="checkbox" aria-hidden="true">{{ task.isCompleted ? '✓' : '' }}</span>
            {{ task.title }}
          </button>
          <button type="button" class="delete" (click)="removeTask(task)" aria-label="Eliminar tarea">×</button>
        </li>
      } @empty {
        <li class="empty">Todavía no hay tareas. Es un buen momento para crear la primera.</li>
      }
    </ul>
  }

```
</CodeBlock>

Sintaxis nueva, de arriba a abajo:

- **`{{ ... }}`** (interpolación) — inserta el resultado de una expresión de TypeScript como texto. `{{ errorMessage() }}` funciona porque, como viste antes, un signal se lee llamándolo como función.
- **`(ngSubmit)="addTask()"`** — un *event binding*: ejecuta `addTask()` cuando el formulario se envía (al presionar Enter o hacer clic en el botón `submit`), en vez de recargar la página como haría un `<form>` HTML normal.
- **`[(ngModel)]="newTitle"`** — *two-way binding*: mantiene sincronizados el valor del `<input>` y la propiedad `newTitle` del componente en ambas direcciones, gracias al `FormsModule` que importaste en el paso anterior.
- **`@if (errorMessage()) { ... }`** — el control flow moderno de Angular (parte 1): el bloque solo se renderiza si la expresión entre paréntesis es verdadera. Como `errorMessage()` empieza como `''` (string vacío, que JavaScript trata como falso), este mensaje no aparece hasta que ocurra un error real.
- **`@if (isLoading()) { ... } @else { ... }`** — dos estados mutuamente excluyentes: mientras `isLoading()` sea verdadero, se muestra "Cargando tareas..."; en cuanto pase a `false`, Angular renderiza el bloque `@else` en su lugar.
- **`@for (task of tasks(); track task.id) { ... } @empty { ... }`** — itera sobre el arreglo que devuelve `tasks()`. `track task.id` (obligatorio en la nueva sintaxis) le dice a Angular cómo identificar cada elemento entre un render y el siguiente, para actualizar solo lo que cambió en vez de destruir y recrear toda la lista. El bloque `@empty` se muestra en su lugar si el arreglo está vacío — reemplaza tener que escribir esa condición a mano con un `@if` separado.
- **`[class.completed]="task.isCompleted"`** — un *property binding* especial para clases CSS: añade la clase `completed` al elemento solo si `task.isCompleted` es verdadero, y la quita automáticamente si vuelve a ser falso.
- **`(click)="toggleTask(task)"`** — otro *event binding*, esta vez para un clic. Fíjate que le pasas `task` (la tarea de esta iteración específica del `@for`) como argumento, para que el método sepa exactamente cuál de todas las tareas cambiar.

Los estilos pueden ser tan simples como el resto de la app. Lo importante es que los estados estén representados: carga, error, lista vacía y tarea completada.

## Decisiones que conviene llevarte

### ¿Por qué Minimal API?

Porque reduce el ruido accidental en una primera vertical slice. No significa que todos los sistemas deban tener endpoints en `Program.cs`; cuando crezca el dominio, puedes mover cada grupo a un método de extensión o a módulos separados sin cambiar el contrato HTTP.

### ¿Por qué no devolver la entidad de EF?

La entidad pertenece al modelo de persistencia. Un contrato de respuesta permite ocultar columnas, renombrar propiedades o componer datos sin crear una migración de base de datos por cada decisión de frontend.

### ¿Por qué el proxy y no CORS abierto?

El proxy resuelve el origen durante desarrollo. En producción el frontend y la API pueden vivir bajo el mismo dominio o puedes configurar una lista explícita de orígenes confiables. `AllowAnyOrigin()` sería cómodo, pero no es una política de seguridad.

### ¿Qué falta para producción?

Autenticación, validación centralizada, logging estructurado, health checks, migraciones ejecutadas como paso de despliegue, una base de datos gestionada y tests automáticos. No son adornos: son las piezas que convierten el quickstart en un servicio mantenible.
