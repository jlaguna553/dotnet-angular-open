Este capítulo es una **vertical slice**: una pieza pequeña, pero completa, que atraviesa base de datos, servidor y navegador. Al terminar tendrás una aplicación de tareas donde puedes listar, crear, completar y eliminar registros.

La app no intenta esconder la complejidad detrás de una plantilla. Cada decisión está a la vista para que puedas cambiarla después.

## El resultado que vamos a construir

La arquitectura será deliberadamente pequeña:

```text
browser (Angular 17+)
        │ HTTP / JSON
        ▼
ASP.NET Core 8 Minimal API
        │ EF Core
        ▼
SQLite (tasks.db)
```

Cada capa de ese diagrama es una tecnología con un rol concreto. **ASP.NET Core** es el framework de Microsoft para construir servidores web en C# — es lo que recibe la petición HTTP y decide qué código ejecutar. **SQLite** es el motor de base de datos: un programa que guarda tus datos en un archivo y sabe responder consultas sobre ellos.

Entre ambos falta una pieza: tu código C# trabaja con **objetos** (una clase `TaskItem` con propiedades), pero SQLite solo entiende **SQL** (`SELECT * FROM Tasks WHERE ...`). Traducir entre esos dos mundos a mano —escribir el SQL, ejecutarlo, convertir cada fila del resultado de vuelta a un objeto `TaskItem`— es exactamente el trabajo repetitivo que quieres evitar. Ahí entra **EF Core** (*Entity Framework Core*, así, con esas iniciales): un **ORM** (*Object-Relational Mapper*, "mapeador objeto-relacional") de Microsoft que hace esa traducción por ti. Le describes tus datos como clases de C# normales, y EF Core se encarga de generar el SQL, ejecutarlo contra SQLite (o Postgres, o SQL Server — con solo cambiar el "proveedor", como verás en el paso 1), y devolverte objetos ya listos para usar. En el paso 3 vas a escribir tu primer `DbContext`, que es la pieza concreta de EF Core con la que vas a interactuar.

El recurso principal es `TaskItem`:

| Método | Ruta | Acción |
| --- | --- | --- |
| `GET` | `/api/tasks` | Devuelve tareas ordenadas por fecha |
| `POST` | `/api/tasks` | Crea una tarea |
| `PATCH` | `/api/tasks/{id}` | Cambia el estado completado |
| `DELETE` | `/api/tasks/{id}` | Elimina una tarea |

## 1. Crea la solución

Separa backend y frontend desde el primer día. Esto hace visibles los límites y permite desplegarlos de forma independiente — el mismo principio de "cliente-servidor" de la parte 0. Vas a crear tres cosas distintas, cada una con un propósito concreto: una *solución* de .NET (el archivo que agrupa proyectos backend), el proyecto de la API en sí, y el proyecto de Angular como carpeta hermana, no anidada dentro de la API.

Primero, la carpeta raíz y la solución:

<CodeBlock lang="bash" title="Terminal">
```bash
mkdir taskboard && cd taskboard
dotnet new sln -n Taskboard
```
</CodeBlock>

`dotnet new sln` crea `Taskboard.sln`, un archivo vacío que **agrupa proyectos** de .NET para poder compilarlos, testearlos o abrirlos juntos en el editor — todavía no contiene ningún código. Hoy vas a añadirle un solo proyecto, pero en la parte 10 esta misma solución va a crecer a cuatro (`Domain`, `Application`, `Infrastructure`, `Api`); tenerla desde ahora evita reestructurar más adelante.

Ahora el proyecto de la API:

<CodeBlock lang="bash" title="Terminal">
```bash
dotnet new web -n Taskboard.Api
dotnet sln add Taskboard.Api/Taskboard.Api.csproj
```
</CodeBlock>

- `dotnet new web -n Taskboard.Api` genera el proyecto ASP.NET Core más pequeño que existe: solo un `Program.cs` y un `.csproj`, sin controladores ni carpetas de MVC — la plantilla `web` es, precisamente, la que usan las Minimal API que vas a construir en este capítulo. `-n` nombra tanto el proyecto como la carpeta que crea.
- `dotnet sln add ...` **no ocurre automáticamente**: crear un proyecto y registrarlo en la solución son dos pasos separados. Sin este comando, `Taskboard.Api` existiría en el disco pero `dotnet build` a nivel de solución lo ignoraría.

Y el proyecto de Angular, como carpeta hermana de `Taskboard.Api` (no dentro de ella):

<CodeBlock lang="bash" title="Terminal">
```bash
ng new taskboard-web --standalone --routing --style=scss --skip-git
```
</CodeBlock>

Cada flag es una decisión explícita, no un valor arbitrario:

| Flag | Qué hace | Por qué lo usamos aquí |
| --- | --- | --- |
| `--standalone` | Genera componentes sin `NgModule` | Es el enfoque que vas a usar en toda la guía, a partir de la parte 1 |
| `--routing` | Crea `app.routes.ts` con el Router configurado | Este quickstart no navega entre páginas todavía, pero lo necesitarás desde la parte 5 (pantalla de login) |
| `--style=scss` | Usa Sass en vez de CSS plano para las hojas de estilo | Sass te da variables y anidamiento sin coste — puedes escribir CSS normal dentro de un archivo `.scss` si no lo necesitas aún |
| `--skip-git` | No inicializa un repositorio git dentro de `taskboard-web/` | `ng new` crea su propio repo por defecto; lo evitamos porque `taskboard/` en su conjunto será un único repositorio |

Angular CLI te va a preguntar interactivamente sobre Server-Side Rendering (SSR) — responde que no (`N`) por ahora; es el tema que se menciona brevemente en la parte 0 y que queda fuera del alcance de este curso.

### Añade EF Core y las herramientas de migración

Con los dos proyectos creados, instala en `Taskboard.Api` lo necesario para hablar con una base de datos:

<CodeBlock lang="bash" title="Terminal">
```bash
cd Taskboard.Api
dotnet add package Microsoft.EntityFrameworkCore.Sqlite --version 8.*
dotnet add package Microsoft.EntityFrameworkCore.Design --version 8.*
dotnet tool install --global dotnet-ef
cd ..
```
</CodeBlock>

Cada `dotnet add package <nombre>` descarga un **paquete de NuGet** — el registro de librerías de .NET, el equivalente exacto del npm que acabas de usar para instalar Angular CLI — y lo añade como referencia dentro de `Taskboard.Api.csproj` (el archivo XML que lista, entre otras cosas, qué paquetes usa el proyecto).

Son tres piezas distintas, y vale la pena distinguirlas:

- **`Microsoft.EntityFrameworkCore.Sqlite`** es el *proveedor*: la pieza que sabe traducir las operaciones de EF Core al SQL específico de SQLite. Cada motor de base de datos necesita su propio proveedor — en la parte 4 vas a sustituir este paquete por `Npgsql.EntityFrameworkCore.PostgreSQL` sin cambiar ninguna otra línea de código.
- **`Microsoft.EntityFrameworkCore.Design`** trae las herramientas necesarias **solo en tiempo de desarrollo** para generar migraciones (`dotnet ef migrations add`, que verás en el paso 5). No la necesita la aplicación cuando corre en producción, pero sí el propio comando `dotnet ef` para inspeccionar tu proyecto y generar el código de la migración.
- **`dotnet tool install --global dotnet-ef`** es distinto a los dos anteriores: no es un paquete NuGet que se referencia desde el `.csproj`, sino una **herramienta de línea de comandos** que se instala una sola vez en tu máquina (`--global`) y queda disponible como `dotnet ef` en cualquier proyecto, no solo en Taskboard.

## 2. Modela el dominio

Crea `Taskboard.Api/Models/TaskItem.cs`. El modelo representa datos persistidos, no el formulario de entrada. `CreatedAt` lo controla el servidor para que el cliente no pueda falsificarlo.

<CodeBlock lang="csharp" title="Models/TaskItem.cs">
```csharp
namespace Taskboard.Api.Models;

public sealed class TaskItem
{
    public int Id { get; set; }
    public required string Title { get; set; }
    public bool IsCompleted { get; set; }
    public DateTime CreatedAt { get; set; }
}
```
</CodeBlock>

Para evitar aceptar campos que no deberían llegar desde el navegador, define contratos explícitos en `Contracts/TaskContracts.cs`:

<CodeBlock lang="csharp" title="Contracts/TaskContracts.cs">
```csharp
namespace Taskboard.Api.Contracts;

public sealed record CreateTaskRequest(string Title);
public sealed record UpdateTaskRequest(bool IsCompleted);
public sealed record TaskResponse(
    int Id,
    string Title,
    bool IsCompleted,
    DateTime CreatedAt);
```
</CodeBlock>

`record` es un tipo de C# pensado para datos inmutables: escribir `public sealed record CreateTaskRequest(string Title);` genera automáticamente el constructor, la comparación por valor (dos records son "iguales" si sus datos coinciden, no solo si son el mismo objeto en memoria) y una representación en texto legible — todo lo que tendrías que escribir a mano con una `class` tradicional. Es la elección natural para contratos que solo transportan datos entre capas, sin comportamiento propio.

La respuesta pública no tiene por qué coincidir con la entidad de EF Core. Esa pequeña separación evita acoplar tu API a futuras decisiones de persistencia.

## 3. Configura EF Core y SQLite

Crea `Data/TaskDbContext.cs`:

<CodeBlock lang="csharp" title="Data/TaskDbContext.cs">
```csharp
using Microsoft.EntityFrameworkCore;
using Taskboard.Api.Models;

namespace Taskboard.Api.Data;

public sealed class TaskDbContext(DbContextOptions<TaskDbContext> options)
    : DbContext(options)
{
    public DbSet<TaskItem> Tasks => Set<TaskItem>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<TaskItem>(entity =>
        {
            entity.Property(task => task.Title)
                .HasMaxLength(160)
                .IsRequired();

            entity.Property(task => task.CreatedAt)
                .HasDefaultValueSql("CURRENT_TIMESTAMP");
        });
    }
}
```
</CodeBlock>

`public sealed class TaskDbContext(DbContextOptions<TaskDbContext> options) : DbContext(options)` usa **constructores primarios** (C# 12): los parámetros entre paréntesis junto al nombre de la clase reemplazan escribir un constructor y un campo privado por separado. Y nunca vas a escribir `new TaskDbContext(...)` en ningún lado — quién construye esta clase, y cuándo, es exactamente lo que verás en el siguiente paso.

En `appsettings.json`, configura la conexión con un archivo local. En producción sustituirás esta cadena por una variable de entorno.

<CodeBlock lang="json" title="appsettings.json">
```json
{
  "ConnectionStrings": {
    "Taskboard": "Data Source=taskboard.db"
  },
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  }
}
```
</CodeBlock>

## 4. Construye la API Minimal

Reemplaza el contenido de `Program.cs`. La aplicación registra CORS para el servidor de desarrollo de Angular, crea la base de datos al arrancar y expone cuatro operaciones HTTP.

<CodeBlock lang="csharp" title="Program.cs">
```csharp
using Microsoft.EntityFrameworkCore;
using Taskboard.Api.Contracts;
using Taskboard.Api.Data;
using Taskboard.Api.Models;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<TaskDbContext>(options =>
    options.UseSqlite(builder.Configuration.GetConnectionString("Taskboard")));

builder.Services.AddCors(options =>
{
    options.AddPolicy("AngularDev", policy => policy
        .WithOrigins("http://localhost:4200")
        .AllowAnyHeader()
        .AllowAnyMethod());
});

var app = builder.Build();

app.UseCors("AngularDev");

using (var scope = app.Services.CreateScope())
{
    var database = scope.ServiceProvider.GetRequiredService<TaskDbContext>();
    await database.Database.MigrateAsync();
}

app.MapGet("/api/tasks", async (TaskDbContext database, CancellationToken cancellationToken) =>
{
    var tasks = await database.Tasks
        .AsNoTracking()
        .OrderByDescending(task => task.CreatedAt)
        .Select(task => new TaskResponse(
            task.Id,
            task.Title,
            task.IsCompleted,
            task.CreatedAt))
        .ToListAsync(cancellationToken);

    return Results.Ok(tasks);
});

app.MapPost("/api/tasks", async (
    CreateTaskRequest request,
    TaskDbContext database,
    CancellationToken cancellationToken) =>
{
    var title = request.Title.Trim();
    if (title.Length is < 1 or > 160)
    {
        return Results.ValidationProblem(new Dictionary<string, string[]>
        {
            [nameof(request.Title)] = ["Escribe entre 1 y 160 caracteres."]
        });
    }

    var task = new TaskItem
    {
        Title = title,
        CreatedAt = DateTime.UtcNow
    };

    database.Tasks.Add(task);
    await database.SaveChangesAsync(cancellationToken);

    return Results.Created($"/api/tasks/{task.Id}", new TaskResponse(
        task.Id, task.Title, task.IsCompleted, task.CreatedAt));
});

app.MapPatch("/api/tasks/{id:int}", async (
    int id,
    UpdateTaskRequest request,
    TaskDbContext database,
    CancellationToken cancellationToken) =>
{
    var task = await database.Tasks.FindAsync([id], cancellationToken);
    if (task is null)
    {
        return Results.NotFound();
    }

    task.IsCompleted = request.IsCompleted;
    await database.SaveChangesAsync(cancellationToken);
    return Results.NoContent();
});

app.MapDelete("/api/tasks/{id:int}", async (
    int id,
    TaskDbContext database,
    CancellationToken cancellationToken) =>
{
    var deleted = await database.Tasks
        .Where(task => task.Id == id)
        .ExecuteDeleteAsync(cancellationToken);

    return deleted == 0 ? Results.NotFound() : Results.NoContent();
});

app.Run();

public partial class Program { }
```
</CodeBlock>

Antes de los detalles puntuales, dos conceptos que se repiten en **cada** endpoint y que vale la pena nombrar:

- **Inyección de dependencias (DI).** Fíjate que en `(TaskDbContext database, CancellationToken cancellationToken) => { ... }` nunca escribes `new TaskDbContext(...)` — `database` simplemente aparece como parámetro, ya listo para usar. Esto es DI: le dijiste al framework, con `builder.Services.AddDbContext<TaskDbContext>(...)`, *cómo* construir un `TaskDbContext` cuando alguien lo necesite. ASP.NET Core inspecciona los parámetros de cada handler, reconoce que pide un `TaskDbContext`, y te entrega una instancia ya configurada — una nueva por cada petición HTTP. No lo pasas a mano por ningún lado; el framework lo resuelve por ti a partir del tipo declarado. Vas a ver la misma idea, con otro nombre (`inject()`), del lado de Angular en el paso 7.
- **`async`/`await` y `CancellationToken`.** Marcar un método como `async` y usar `await` dentro le permite al servidor seguir atendiendo otras peticiones mientras espera algo lento —aquí, una consulta a la base de datos— en lugar de bloquear un hilo sin hacer nada mientras tanto. `CancellationToken` es una señal que ASP.NET Core te pasa automáticamente y que se activa si el cliente cierra la conexión antes de que termines de responder, para que puedas abandonar el trabajo a medio hacer en vez de completarlo igual sin que nadie vaya a leer el resultado.

Y tres detalles más puntuales que vale la pena observar:

1. `AsNoTracking()` hace explícito que el listado es de solo lectura.
2. `Results.Created` devuelve el recurso creado y su URL en el encabezado `Location`.
3. `public partial class Program` permite que los tests de integración encuentren el entry point.

## 7. Encapsula el acceso HTTP

El servicio es la única pieza que conoce las rutas de la API. Esa frontera hace que el componente pueda concentrarse en interacción y estado.

<CodeBlock lang="typescript" title="src/app/services/task-api.service.ts">
```typescript
import { Injectable, inject } from '@angular/core';
import { HttpClient } from '@angular/common/http';
import { Observable } from 'rxjs';
import { CreateTaskRequest, Task } from '../models/task';

@Injectable({ providedIn: 'root' })
export class TaskApiService {
  private readonly http = inject(HttpClient);
  private readonly resourceUrl = '/api/tasks';

  getAll(): Observable<Task[]> {
    return this.http.get<Task[]>(this.resourceUrl);
  }

  create(request: CreateTaskRequest): Observable<Task> {
    return this.http.post<Task>(this.resourceUrl, request);
  }

  updateStatus(id: number, isCompleted: boolean): Observable<void> {
    return this.http.patch<void>(`${this.resourceUrl}/${id}`, { isCompleted });
  }

  remove(id: number): Observable<void> {
    return this.http.delete<void>(`${this.resourceUrl}/${id}`);
  }
}
```
</CodeBlock>

Tres piezas nuevas en este servicio, y las tres relacionadas entre sí:

- **`@Injectable({ providedIn: 'root' })`** marca la clase como disponible para el sistema de inyección de dependencias de Angular — la misma idea de DI que viste en el backend en el paso 4, ahora del lado del cliente. `providedIn: 'root'` significa que existe una única instancia compartida por toda la aplicación (un *singleton*), no una nueva cada vez que algo la pide.
- **`inject(HttpClient)`** es cómo `TaskApiService` obtiene esa dependencia: en vez de crear su propio cliente HTTP con `new`, le pide a Angular que le entregue la instancia ya configurada — la que vas a registrar con `provideHttpClient()` a continuación.
- **`Observable<Task[]>`** es el tipo que devuelve cada método de `HttpClient`. Se parece a una `Promise` de JavaScript (representa un valor que llegará más adelante), pero con una diferencia clave: **no hace nada hasta que alguien se suscribe** con `.subscribe(...)`, algo que verás en el paso 8. Puede además emitir varios valores a lo largo del tiempo, en vez de uno solo. Profundizamos en RxJS —la librería detrás de `Observable`— en la parte 2.

Registra `HttpClient` en `src/app/app.config.ts`:

<CodeBlock lang="typescript" title="src/app/app.config.ts">
```typescript
import { ApplicationConfig } from '@angular/core';
import { provideHttpClient } from '@angular/common/http';
import { provideRouter } from '@angular/router';
import { routes } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideRouter(routes),
    provideHttpClient(),
  ],
};
```
</CodeBlock>

## 8. Construye el componente

Este componente usa APIs standalone y `@if`/`@for`, el control flow moderno de Angular. El formulario es nativo en este quickstart para mantener el foco en el flujo HTTP; en la parte 2 lo sustituiremos por Reactive Forms.

<CodeBlock lang="typescript" title="src/app/app.component.ts">
```typescript
import { Component, OnInit, inject, signal } from '@angular/core';
import { FormsModule } from '@angular/forms';
import { Task } from './models/task';
import { TaskApiService } from './services/task-api.service';

@Component({
  selector: 'app-root',
  standalone: true,
  imports: [FormsModule],
  templateUrl: './app.component.html',
  styleUrl: './app.component.scss',
})
export class AppComponent implements OnInit {
  private readonly taskApi = inject(TaskApiService);

  readonly tasks = signal<Task[]>([]);
  readonly isLoading = signal(true);
  readonly errorMessage = signal('');
  newTitle = '';

  ngOnInit(): void {
    this.loadTasks();
  }

  loadTasks(): void {
    this.isLoading.set(true);
    this.taskApi.getAll().subscribe({
      next: (tasks) => {
        this.tasks.set(tasks);
        this.isLoading.set(false);
      },
      error: () => {
        this.errorMessage.set('No pudimos cargar las tareas. ¿Está encendida la API?');
        this.isLoading.set(false);
      },
    });
  }

  addTask(): void {
    const title = this.newTitle.trim();
    if (!title) return;

    this.taskApi.create({ title }).subscribe({
      next: (task) => {
        this.tasks.update((tasks) => [task, ...tasks]);
        this.newTitle = '';
      },
      error: () => this.errorMessage.set('La tarea no pudo guardarse.'),
    });
  }

  toggleTask(task: Task): void {
    this.taskApi.updateStatus(task.id, !task.isCompleted).subscribe({
      next: () => this.tasks.update((tasks) => tasks.map((item) =>
        item.id === task.id ? { ...item, isCompleted: !item.isCompleted } : item)),
      error: () => this.errorMessage.set('No pudimos actualizar la tarea.'),
    });
  }

  removeTask(task: Task): void {
    this.taskApi.remove(task.id).subscribe({
      next: () => this.tasks.update((tasks) => tasks.filter((item) => item.id !== task.id)),
      error: () => this.errorMessage.set('No pudimos eliminar la tarea.'),
    });
  }
}
```
</CodeBlock>

Una pieza más que aparece por primera vez: `signal<Task[]>([])` crea un **signal**, un contenedor de estado que Angular sabe leer y "escuchar". Cuando lo actualizas con `.set(...)` o `.update(...)`, Angular sabe exactamente qué parte de la plantilla depende de ese valor y solo repinta eso, sin que tengas que decírselo tú. Por ahora, quédate con dos reglas prácticas: para leer su valor lo **llamas como función** (`tasks()`, nunca `tasks`), y nunca lo mutas directamente (nada de `tasks().push(...)`). Vas a profundizar en signals, junto con `computed` y `effect`, en la parte 1.

La plantilla queda pequeña porque el componente mantiene la lógica en métodos con nombres claros:

<CodeBlock lang="html" title="src/app/app.component.html">

Los códigos de estado que esperamos son:

- `200 OK` para el listado.
- `201 Created` para la creación.
- `204 No Content` para actualizar y borrar.
- `404 Not Found` si se intenta actualizar o borrar un id inexistente.
- `400 Bad Request` o `422 Unprocessable Entity` para un título inválido, según cómo centralices la validación.

## Decisiones que conviene llevarte

### ¿Por qué Minimal API?

Porque reduce el ruido accidental en una primera vertical slice. No significa que todos los sistemas deban tener endpoints en `Program.cs`; cuando crezca el dominio, puedes mover cada grupo a un método de extensión o a módulos separados sin cambiar el contrato HTTP.

### ¿Por qué no devolver la entidad de EF?

La entidad pertenece al modelo de persistencia. Un contrato de respuesta permite ocultar columnas, renombrar propiedades o componer datos sin crear una migración de base de datos por cada decisión de frontend.

### ¿Por qué el proxy y no CORS abierto?

El proxy resuelve el origen durante desarrollo. En producción el frontend y la API pueden vivir bajo el mismo dominio o puedes configurar una lista explícita de orígenes confiables. `AllowAnyOrigin()` sería cómodo, pero no es una política de seguridad.

### ¿Qué falta para producción?

Autenticación, validación centralizada, logging estructurado, health checks, migraciones ejecutadas como paso de despliegue, una base de datos gestionada y tests automáticos. No son adornos: son las piezas que convierten el quickstart en un servicio mantenible.
